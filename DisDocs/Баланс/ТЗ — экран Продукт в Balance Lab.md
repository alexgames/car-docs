# ТЗ — экран «Продукт» в Balance Lab

## Зачем нужен экран

«Продукт» — главный дашборд геймдизайнера для **одного баланс-профиля**. Он не редактирует CSV построчно и не повторяет экран «Конфиги». Его задача — ответить на вопрос: **будет ли игра оставаться интересной для разных игроков в каждый период жизни аккаунта, и какую экономику для этого нужно сгенерировать?**

Экран задаёт продуктовые решения. По ним генератор создаёт игровые конфиги с ценами и наградами. Текущие вкладки Balance Lab затем читают эти конфиги и проверяют реальные пути игроков.

Единица времени во всём экране — **календарный день**, а не число сессий. Арена, дейлики и rewarded-реклама описываются как доступные действия дня.

## Границы и термины

- **Баланс-профиль** — набор продуктовых решений; например, `2.0 baseline`, позже — `2.0 A`, `2.0 B`.
- **Продуктовый каталог** — список контента с ID, типом, субъективной ценностью и способом получения. Он редактируется отдельно во вкладке «Конфиги» как CSV.
- **Игровые конфиги** — сгенерированные цены, награды и доступность в формате, который читает игра и симулятор.
- Экран не должен принимать старые случайные цены за входные данные. Текущий пул контента — материал для классификации, а не источник баланса.

## 1. Шапка баланс-профиля

Параметры:

| Параметр | Для чего |
|---|---|
| ID и название профиля | Сохранять baseline и будущие A/B-варианты рядом, не смешивая их. |
| Статус | Черновик / на плейтесте / кандидат в релиз / архив. |
| Версия и дата | Понимать, какие решения породили конкретные игровые конфиги. |
| Описание гипотезы | Например: «более быстрый ранний темп без усиления рекламы». |
| Комментарий об изменении | Что изменилось относительно предыдущего профиля и зачем. |
| Seed генерации | Повторяемо получать те же цены при тех же параметрах. Новый seed — отдельное осознанное изменение, а не случайный дрейф. |

## 2. Неподвижные решения версии

Это переключатели, а не цены.

| Решение | Значение для 2.0 |
|---|---|
| Workshop и базовое творчество | доступны без пейвола |
| XP и уровни | выключены |
| Бусты | выключены; будущая отдельная фича, не часть экономики 2.0 |
| Базовый прогресс | Арена + дейлик + контентные цели |
| Кристаллы | не нужны для базового творчества |
| Promo | дополнительный эксклюзивный контент, не обязательный путь силы |
| Premium-корпуса | гипотеза: только premium или promo; не выдаются за soft/hard до отдельного решения |

Экран должен показывать эти решения как видимый «контракт версии», чтобы случайно не вернуть XP или бусты при настройке цифр.

## 3. Сегменты игроков

Для каждого сегмента задаются не цены, а ожидаемое поведение в день.

| Параметр сегмента | Что задаёт геймдизайнер |
|---|---|
| Название и мотивация | Автор, умеренный автор, коллекционер, платящий ускоритель и т. п. |
| Активные дни | В какие календарные дни игрок обычно заходит. |
| Арена | Сколько осмысленных работ/участий в день. |
| Дейлики | Какие типы заданий игрок обычно выполняет: основной, сложный, социальный. |
| Rewarded | Сколько добровольных показов в день игрок готов смотреть. |
| Предпочтения контента | Что выбирает раньше: стили, Экстры, инструменты, апгрейды, промо. |
| Платёжное поведение | Не платит / покупает ускорение / коллекционирует premium. |

Минимальные сегменты для первого профиля: активный бесплатный автор, умеренный бесплатный автор, платящий - слабо/средне/кит. Позже добавляются A/B-профили поведения, а не копии одних и тех же игроков.

## 4. Цели интереса по жизненному циклу

Главная таблица экрана. В ней геймдизайнер задаёт, **какую новую причину вернуться** должен получить игрок в каждом диапазоне дней.

Обязательные поля каждой строки:

| Поле | Смысл |
|---|---|
| Диапазон дней | Например 1–3, 4–10, 11–30, 31–90, 91–365. Редактируемый. |
| Эмоция/потребность игрока | «Я уже могу сделать классную машину», «хочу попробовать следующий стиль», «собираю личную мастерскую». |
| Главная цель периода | Новая возможность, а не просто число валюты. |
| Минимальная частота новой цели | Сколько дней игрок не должен оставаться без новой творческой причины вернуться. |
| Типы допустимых наград | Экстра, инструмент, стиль, апгрейд, промо, premium-витрина. |
| Целевой объём открытия | Сколько объектов каждого типа игрок получает в этом периоде. |
| Канал получения | Арена, основной дейлик, сложное задание, rewarded, промо, покупка. |
| Уровень дефицита | Свободно / коплю несколько дней / редкая большая цель / только premium или promo. |

Стартовые интервалы — только шаблон, их можно менять: 1–3, 4–10, 11–30, 31–90, 91–365. После ранней фазы темп должен стать ровнее, но не исчезнуть: активный автор не должен ждать новую творческую цель дольше заранее заданного лимита.

## 5. Вехи прогрессии

Веха — конкретное условие, по которому затем валидируется отчёт симулятора. Для каждой вехи нужны поля:

| Параметр | Пример смысла |
|---|---|
| ID и название | `first_extra`, `style_2`, `pro_3_styles`, `first_upgrade`, `all_launch_styles`. |
| Получатель | Один или несколько сегментов. |
| Условие | Получен предмет типа; открыто N стилей; доступен ПРО; получен promo-контент. |
| Целевое окно в днях | Ранний / ожидаемый / крайний день. |
| Приоритет | Обязательно, желательно, долгосрочно. |
| Объяснение | Какую часть интереса игрока защищает эта веха. |

Обязательные вехи 2.0: первая Экстра, первый инструмент, второй стиль, третий стиль/ПРО, первый апгрейд, все стартовые стили, первый promo-предмет, первая premium-витрина. **Числа в них задаются геймдизайнером в профиле, а не зашиваются в код интерфейса.**

## 6. Контентная классификация и крещендо

Полная логика, по которой из витрины, времени, дефицита и коэффициентов выводятся цены, описана в [[Модель формирования цен 2.0]]. Экран не хранит цены как первичную истину: он показывает и редактирует входные параметры модели.

Каталог контента должен содержать не цену, а продуктовую оценку, из которой цена выводится генератором.

| Поле каталога | Варианты / смысл |
|---|---|
| ID | Реальный игровой ID. |
| Тип | Стиль, Экстра, инструмент, апгрейд, корпус, декаль, premium-машина. |
| Рейтинг ценности | 1–10: насколько предмет желанен/заметен/расширяет творчество. Субъективная, но явная оценка геймдизайнера. |
| Сложность | 1–10: насколько предмет требует освоения или меняет творческий процесс. |
| Предпочтительная экономика | soft / hard / real / promo / free. |
| Способ получения | Прогресс, сложный дейлик, premium, промо-код, тематическое событие. |
| Доступность | Старт, день/период, тематическая волна, ограниченная promo-акция. |
| Совместимость | Стиль/стили, для которых предмет имеет смысл. |
| Причина | Короткая заметка: почему предмет стоит именно этой экономики. |

Параметры крещендо на экране:

- базовая цена по типу и валюте;
- вклад рейтинга и сложности в цену;
- кривая роста цены для последующих предметов того же типа;
- минимальная и максимальная цена в каждом периоде;
- допустимый разброс цен внутри одинаковой ценности;
- запретные сочетания: например, корпус нельзя сгенерировать за soft/hard, promo нельзя купить за real без отдельного решения.

Важно: разброс цен должен быть **детерминирован seed**, иначе повторный расчёт меняет баланс без продуктовой причины. Изменение seed — записываемое изменение профиля.

## 7. Источники валюты и награды за дейлики

Экран задаёт бюджет дня, а не старые случайные награды.

| Параметр | Что задаётся |
|---|---|
| Награда Арены | Монеты/другие разрешённые ресурсы за базовое участие дня. |
| Основной дейлик | Награда за действие, которое усиливает core loop. |
| Лёгкий дейлик | Маленькая награда за обучение/персонализацию, не обязательная для темпа. |
| Сложный дейлик | Больше soft и/или немного hard за бриф, чертёж, сложную творческую задачу. |
| Социальный дейлик | Promo-токен или малая награда; не должен быть обязательным. |
| Rewarded | Награда за показ, лимит показов в день, доступность по дням жизни. |
| Promo-коды | Какие типы контента выдаются, лимиты и срок кампании. |
| Компенсации и подарки | Явный источник, чтобы не создавать невидимую инфляцию. |

Экран должен показывать сводку: сколько soft/hard/promo в среднем получает каждый сегмент в день и в каждом диапазоне дней. Это главный input генератора цен.

## 8. Промо и контент-маркетинг

Промо — основа контентной петли, а не скрытая скидка.

Параметры:

- ритм новых кодов и тематических активностей;
- тип награды: декаль, Экстра, корпус, инструментальный приём, коллекционный предмет;
- эксклюзивность: уникальный, сезонный, постоянно доступный после ввода;
- источник: видео, соцсеть, челлендж, реферальная механика;
- привязка к теме/стилю/маркетинговому ролику;
- максимальное время без нового promo-повода для активного игрока.

Интерфейсная идея: на главной есть вход в экран промо и ввод кодов; в конце списков деталей две отдельные карточки — `+` для магазина и `+ promo` для эксклюзивов из роликов. Это две прямые, не скрытые ветки; промежуточный экран выбора не нужен.

## 9. Монетизация и ограничения

Экран должен содержать не только цены, но и защитные ограничения:

- базовое творчество, стартовые детали и Workshop не продаются как снятие боли;
- hard-валюта не блокирует первый хороший результат;
- premium продаёт уникальность/коллекционирование/удобство, не возможность играть;
- remove ads и interstitial настраиваются отдельно от выдачи rewarded;
- interstitial не показывается в первые 30 секунд сессии и не мешает первой сессии;
- бусты выключены в 2.0.

## 10. Результат генерации и проверка

Кнопка **«Сгенерировать игровые конфиги»** должна:

1. Сохранить снимок баланс-профиля.
2. Создать игровые CSV в отдельной версии/папке, не перезаписывая релизные конфиги без явного действия.
3. Показать diff: какие цены, награды и доступность изменились относительно предыдущего профиля.
4. Запустить симуляции текущих профилей игроков на новых CSV.
5. Сформировать отчёт «веха → факт → целевое окно → вердикт».
6. Подсветить причину провала: не хватает дохода, цена слишком высока, мало подходящего контента в периоде, неверный приоритет сегмента.

## Что не делать в первой версии экрана

- Не строить A/B-менеджер до появления реальных экспериментов.
- Не перезаписывать боевые конфиги одной кнопкой.
- Не генерировать цену для real/promo-контента без явно выбранной продуктовой политики.
- Не выдавать рекомендацию только по среднему игроку: нужен отдельный отчёт для каждого сегмента.
- Не считать текущий контент «правильным» только потому, что он уже существует.
