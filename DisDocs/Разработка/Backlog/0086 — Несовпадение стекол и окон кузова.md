# Несовпадение стекол и окон кузова

## Проблема

У некоторых комбинаций кузова стекло не совпадает с оконным проёмом. Проверенный
пример:

`formula: [49-41-30-35]`, `cab2 = 30.

Стекло выступает за стойки и имеет контур, заметно отличающийся от проёма. Ошибка
видна в диагностическом режиме `SROptions → Cheat → Low Poly Car`, то есть возникает
до OpenSubdiv и не связана со сглаживанием. Пока комбинацию оставляем как есть.

## Основные гипотезы

1. Дизайнерская ошибка: стекло и кузов изначально сделаны для разных контуров.
2. Неверная связь вариантов: для `cab2 = 41` подставляется стекло от другого варианта.
3. Ошибка в иерархии или трансформах одного из объектов большого FBX.
4. Ошибка импорта/экспорта FBX. Это менее вероятно: Unity обычно не меняет форму
   отдельного меша, но нужно проверить axis conversion, scale и вложенные transforms.

## Диагностика

- [x] Сравнить сглаженный и low-poly результат — ошибка присутствует в low-poly.
- [ ] Найти source mesh кузова, проёма и стекла для `cab2 = 41` в большом FBX.
- [ ] Проверить, соответствует ли ID стекла ID кузовной детали в таблицах сборки.
- [ ] Сравнить вершины source FBX и импортированного Unity mesh в мировых координатах.
- [ ] Проверить transforms родителей, `Bake Axis Conversion`, scale и настройки FBX importer.
- [ ] Проверить соседние варианты `cab2`, чтобы определить единичная это ошибка или
      системное смещение индексов.

## Предпочтительный ремонт без 3D-дизайнера

Не исправлять форму во время каждой сборки машины. Сделать редакторский инструмент,
который создаёт исправленный mesh-asset один раз и сохраняет его как override для
конкретного варианта.

### Вариант A — ручная коррекция вершин в Unity

1. Извлечь стекло конкретного варианта в отдельный mesh asset.
2. Редактировать его вершины в Unity/ProBuilder либо простым собственным cage-инструментом.
3. Сохранить результат в `Assets/Addr_dynamic`.
4. В таблице исправлений хранить связь `part type + variant ID → corrected mesh`.

Это самый надёжный и дешёвый вариант для нескольких проблемных стёкол. Исходный FBX
остаётся неизменным, исправление обратимо и не требует runtime-расчёта.

### Вариант B — параметры коррекции на уровне данных

Для небольших ошибок хранить на вариант:

- локальный offset;
- scale по двум осям плоскости окна;
- shear верхнего/нижнего и переднего/заднего края.

Обычного `Transform` недостаточно, если контуры действительно разные. Нужна хотя бы
четырёхугольная cage-деформация. После настройки результат также лучше запечь в mesh.

### Вариант C — автоматическая подгонка по проёму

Редакторский прототип может:

1. спроецировать стекло и границу оконного проёма на локальную плоскость;
2. извлечь их внешние контуры;
3. построить 4–8-точечный cage по проёму;
4. деформировать вершины стекла билинейно или mean-value coordinates;
5. сохранить исправленный mesh.

Это полезно, если ошибок много, но для одного `cab2 = 41` дороже ручной коррекции.
Автоматическая подгонка должна быть authoring-инструментом, а не runtime-фичей.

## Решение после диагностики

- Если найден неверный ID — исправить только mapping данных.
- Если source FBX правильный, а Unity mesh нет — исправить importer/transforms.
- Если source FBX уже неправильный — использовать baked mesh override до появления
  возможности поправить исходник в 3D-программе.
- Не маскировать проблему дополнительным сглаживанием или изменением материала стекла.

## Чек-лист завершения

- [ ] Стекло `cab2 = 41` полностью находится внутри оконного проёма.
- [ ] Исправление работает в low-poly и smoothed режимах.
- [ ] Не повреждены нормали, UV и vertex colors стекла.
- [ ] Car Glass и генерация UV продолжают работать.
- [ ] Override не добавляет расчётов при каждой сборке машины.
- [ ] Проверена симметричная сторона кузова и открывающиеся двери, если применимо.
