# Описание

Сбор email через waitlist Android-версии и лид-магниты. Контакты используются для редких продуктовых и маркетинговых писем: уведомление о выходе Android-версии, важные обновления проекта и короткие автоматические цепочки после получения лид-магнита.

## Архитектурное решение — 2026-08-18

### Разделение почты

- Обычная бизнес-почта (`hello@cardesign.game`, личные адреса, переписка с партнёрами) размещается отдельно, предварительно — в Timeweb вместе с хостингом сайта.
- Массовые, маркетинговые и автоматические письма не отправляются через SMTP бизнес-почты Timeweb.
- Для рассылок используется Amazon SES напрямую через API.
- Sendy, Mailchimp и аналогичная внешняя CRM рассылок на первом этапе не используются.

Причина: контакты и сегменты уже принадлежат приложению, HTML можно создавать локально, а письма отправляются редко. Тарифы с оплатой за размер базы невыгодны при 10–20 тысячах ожидающих пользователей. Amazon SES оплачивается преимущественно за фактически отправленные письма.

### Поток данных

`собственная база → выбор сегмента → готовый HTML + text-версия → Amazon SES API → события доставки обратно в собственную базу`

Сайт, приложение и база не обязаны размещаться в AWS. В AWS используется только SES; сервер и база могут оставаться в Timeweb или в другой выбранной инфраструктуре.

### Источник истины

Собственная база проекта остаётся источником истины для контактов и сегментов. Для каждого контакта следует хранить как минимум:

- email в нормализованном виде;
- дату и источник подписки;
- основание согласия / версию текста согласия;
- язык и страну, если известны;
- платформу и сегмент (`android_waitlist`, лид-магнит и т. п.);
- статус подписки;
- дату последнего письма;
- unsubscribe, hard bounce и complaint;
- идентификаторы кампаний и основные события отправки.

Контакт с `unsubscribe`, `hard_bounce` или `complaint` не должен снова попадать в маркетинговую отправку.

### Что используется в Amazon SES

- SES API v2 для персональной отправки каждому получателю;
- DKIM, SPF и DMARC для `cardesign.game`;
- отдельный адрес отправителя, предварительно `updates@cardesign.game`;
- собственный MAIL FROM;
- contact list / topics и one-click unsubscribe;
- account-level suppression list;
- configuration set для событий;
- события delivery, bounce, complaint, open и click;
- при необходимости отдельный домен отслеживания, например `links.cardesign.game`.

Новый аккаунт SES сначала находится в sandbox. Перед реальной рассылкой нужно подтвердить домен и запросить production access, описав добровольный Android waitlist и обработку возвратов, жалоб и отписок.

### Метрики

Amazon SES умеет собирать открытия и переходы, но отдаёт их как технические события, а не как полноценную маркетинговую панель. События принимаются приложением и записываются в собственную базу/аналитику.

Открытия являются приблизительной метрикой из-за блокировки изображений и механизмов приватности почтовых клиентов. Основные продуктовые метрики: успешная доставка, hard bounce, complaint, unsubscribe, переход по целевой ссылке и последующая конверсия.

### HTML-письма и ИИ

- HTML создаётся локально с помощью ChatGPT, Claude или других доступных инструментов; AI-дополнение Sendy не требуется.
- Нужен один проверенный шаблон Cardesign с заменяемыми блоками контента.
- Для каждого письма обязательно формируются HTML- и plain-text-версии.
- Email-вёрстка тестируется минимум в Gmail, Apple Mail и Outlook; используются совместимые стили и абсолютные URL ресурсов.
- Обычная подписка ChatGPT подходит для ручной подготовки HTML. Автоматическая генерация из приложения потребует отдельного API и отдельной оплаты.

### Репутация и доставляемость

- На объёме 10–20 тысяч и при редких отправках используется общий пул IP Amazon SES.
- Выделенный IP пока не нужен: ему необходим регулярный объём и прогрев.
- Репутация AWS помогает, но не заменяет репутацию `cardesign.game` и качество базы.
- Старая база не отправляется одним резким залпом без проверки. Первую кампанию следует выпускать контролируемыми партиями и наблюдать за bounce/complaint.
- Waitlist является допустимой базой, если пользователь сам оставил адрес и понимал, что получит уведомление об Android-версии. Для последующего регулярного маркетинга текст согласия должен явно это покрывать.

### Когда вернуться к готовой платформе

Mailchimp, Mailjet, Brevo, Sendy или другой инструмент имеет смысл добавить, если понадобятся:

- постоянная работа нетехнического маркетолога;
- сложный визуальный редактор;
- множество автоматических цепочек;
- сложные A/B-тесты и маркетинговые отчёты;
- управление кампаниями без выпуска изменений в приложении.

До появления этих требований собственная база + прямой SES API проще по данным и дешевле по эксплуатации.

Мейл-сервер поднимать не надо — для транзакционных писем берут готовый сервис (SendGrid, Postmark, Mailgun, AWS SES, Firebase) с готовым API, это часы, а не поднятие своей инфры, плюс так меньше шансов улететь в спам. По кодам — если ваша "готовая система кодов" не заточена под "один код = один email, одноразовый, с истечением", то это отдельный кусок работы (генерация, привязка к email, TTL, защита от повторного использования), а не переиспользование существующей системы как есть.

Так что фича из "быстро прикрутить" превратилась в: транзакционный email-провайдер + отдельная логика одноразовых email-кодов + UI на промо-экране (+ опционально дип-линк позже). Это все еще некритично по объёму, но это уже не пара часов — стоит явно заложить время на провайдера и на код одноразовых кодов, прежде чем обещать сроки.
