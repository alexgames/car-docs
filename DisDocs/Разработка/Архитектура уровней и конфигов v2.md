# Архитектура уровней и конфигов v2

## Зачем менять модель

В версии 1 данные о «задании» разложены между `OrderModel`, `OrderType`, `LevelModel`, `LevelData`, `LevelTaskData`, `CarData`, формулой машины и отдельными файлами зависимостей. Часть этих классов почти не используется, часть дублирует смысл друг друга.

Для версии 2 нужен один гибкий конфиг уровня. Один и тот же уровень может:

- постоянно быть доступен на странице стиля как творческая идея;
- запускаться как свободный Create с заданной стартовой пропорцией;
- иметь эталон и стать заданием на повторение;
- временно попасть в ротацию дейликов;
- позже использоваться в PvE, коллаборации или ином режиме.

Расписание и награда не определяют сам уровень. Они лишь задают способ его показа.

## Основное решение

Главная сущность — **`LevelDef`**. Это описание уровня, независимое от экрана или причины запуска.

```text
LevelDef
  id - строка, совпадает с именем файла
  style - (urban, America, Pro, custom etc)
  title - название уровня или ключ локализации
  comment - любой комментарий, строка
  scene - (необязательно) гараж / шоурум / иной вид сцены
  startCar - CarData (включая базовую деформацию, обвес, цвета, материал, текстуры)
  targetCar (необязательно) - CarData (включая deform и тд)

  reference
    refName - либо модель "Fiat 210", либо общаность "compact short tall"
    comment - любой комментарий, строка (обычно идея референса или описание)
	images:[] - массив имен файлов
	imageTitles:[] (необязательно) - название каждого файла

  edit
    bodyPack (необязательно) - строка со ссылкой на пак деталей
    bodyPackAdd (необязательно) - дополнительный пак в том же формате
    tuningPack - (необязательно) - строка со ссылкой
    tuningPackAdd - (необязательно) - дополнительный пак
    toolPack - (необязательно) - общий набор инструментов
    colorPack - (необязательно), ColorData
    colorPackAdd - (необязательно)
    matPack - MaterialData
    matPackAdd - MaterialData
    decalPack - пак декалей
    decalPackAdd
    bodyLocks:[] - (необязательно)
    deformEdit - (необязательно) оверрайд ограничений базовой деформации:
      points[] - только точки isGuidePoint=false
        pointType
        min
        max
        scoreLimit
    tools:[] - массив строк инструментов
    allowPremium - bool, добавляет в список купленные премиум детали
    allowExtra - bool, добавляет в список купленные экстра детали
    allowPromo - bool
    allowExtraTools- bool, добавляет в список купленные bycnevtyns
  
  scoring (необязательно)
    веса сочетаний ()

  
  
  
```



## Примеры

### Compact: «Короткая»

Это свободный уровень-идея:

- стартовая короткая пропорция;
- нужная схема деформации;
- базовый пул деталей;
- инструменты, которые игроку разрешено менять;
- несколько фото Mini, Renault 5 и Golf как примеры;
- нет эталона, очков и награды.

### «Повтори Mini» - тот же дейлик copyRef

Тот же формат, дополненный:

- эталонной машиной;
- референсы - чертежи
- правилами точного сравнения формы, обвеса и/или цвета;

### Дейлик

Это тот же `LevelDef`, который сервер и баланс временно выбрали для показа. Период показа и награда не являются полями уровня.

Поэтому постоянную идею можно на время сделать дейликом без копирования её конфига.

## Состояние машины
Оставляем существующий **`CarData`**.

- `formula` остаётся: в ней компактно хранятся корпус и детали без локаторов;
- `items` остаётся для деталей с локаторами;
- `deform` в `startCar` — базовая схема именно этой машины.

Деформацию нельзя свободно подменять между машинами: схемы могут быть несовместимы. Поэтому `deformEdit` не заменяет базовый `DeformConfig`, а только переопределяет `min`, `max` и `scoreLimit` у существующих не-guide точек.

## Что происходит со старыми классами

| Старое | Роль в v2 |
|---|---|
| `OrderModel` | временный формат старых заданий; затем удаляется |
| `OrderType` | частный признак старых заданий; не основа новой модели |
| `LevelModel` | не нужен новому формату; ссылка на уровень — его `id` |
| `LevelData` + `LevelTaskData` | сейчас смешивают декларативный конфиг и данные запуска; постепенно заменяются на `LevelDef` и рабочую runtime-модель |
| `CarData` + `formula` + `items` | остаются как есть; это текущий формат снимка машины |

## Редактор уровней

Редактор в Inspector работает только с `LevelDef`.

Минимальные действия автора:

- взять текущую машину как старт;
- применить старт уровня к текущей машине;
- взять и применить схему деформации;
- выбрать доступные части кузова и обвес;
- выбрать доступные инструменты;
- сохранить конфиг.

В режиме автора все инструменты и весь каталог могут быть открыты. В конфиг записывается отдельно, что будет доступно игроку.

### Состав первой панели автора

Панель работает в Unity Inspector. Она редактирует выбранный `LevelDef` и связанные с ним JSON, а не отдельную временную модель.

#### Конфиг

- **Новое название** — поле id. По нему создать новый `LevelDef` как копию текущего, не перезаписывая исходный.
- **Сделать стартовой** — захватить полное состояние машины из сцены: корпус, деформацию, установленный обвес, цвета, материал и текстуру. Сохранить его как новый/обновлённый `StartCarDef` и записать его id в `LevelDef.startCar`.

#### База (`edit`)

- `bodyPack` — dropdown из существующих body-паков.
- `tuningPack` — dropdown из существующих tuning-паков.
- Третье поле «tuning» в исходной заметке требует уточнения: сейчас в модели уже есть `tuningPack`; не создавать дублирующее поле без отдельного смысла.

#### Дополнительный контент (`edit.*Add`)

- **Body:** dropdown типа корпуса, поле id, кнопка **Добавить**, кнопка **Очистить**. Добавляет id в `bodyPackAdd`; очистка удаляет весь дополнительный body-контент.
- **Tuning:** dropdown категории обвеса, поле id, кнопка **Добавить**, кнопка **Очистить**. Добавляет id в `tuningPackAdd`; очистка удаляет весь дополнительный tuning-контент.

Дополнительный контент хранится отдельными паками и в runtime объединяется с базовым без повторов.

#### Инструменты

- все инструменты — набор чекбоксов;
- результат записывается как `edit.tools` (или выбранный `toolPack`, если позже решим оставить библиотеку типовых наборов).

#### Деформация

- dropdown существующих DeformConfig;
- **Применить** — применяет выбранную деформацию к машине в сцене;
- поле имени + **Создать из сцены** — сохраняет текущую деформацию отдельным конфигом и назначает её стартовой деформацией уровня.

## Предзагрузка контента

Предзагрузка не зависит от кнопки `Create`, `Edit` или `Go`.

Она строит единый список из:

- доступного контента `editing`;
- деталей стартовой машины `start`;
- специальных деталей уровня, включая промо;
- иконок этого же списка.

Любой способ запуска уровня вызывает один общий предзагрузчик.

`DebugWorkshopService` не содержит логику подгрузки, применения стартовой машины или преобразования конфигов. Он оставляет только кнопки, которые вызывают соответствующие общие операции.





## Результат уровня

Для v2 используем и постепенно очищаем существующий **`LevelResult`**. Отдельный класс `LevelRes` сейчас не нужен: он только продублирует уже работающий путь таймеров, локального прогресса и отправки на сервер.

`CarData` — снимок машины. Он может быть сохранён, скопирован, отредактирован и повторно использован вне контекста уровня. Результат — событие прохождения: он существует и если игрок вышел без сохранения машины.

```text
LevelResult
  id                    // id попытки, если нужен серверный журнал
  levelDefId            // id LevelDef
  workId?               // появляется только при сохранении машины
  levelTime
  exit
  passed?
  stars?
  score?                // только если у LevelDef есть scoring
  scoreDetails?         // форма / деформация / обвес и т.п.
```

У свободной машины `passed`, `stars` и `score` пустые — это нормально. В `WorkModel` при необходимости достаточно сохранить необязательный `originLevelDefId`, чтобы показать происхождение работы или бейджики. Сам `LevelResult` ссылается на `workId`, а не наоборот.

## Миграция без конвертации

Новые методы добавляются рядом со старыми. Новые уровни создаются и запускаются через `LevelDef`; старые v1-конфиги остаются работать старым путём, пока не будут заменены вручную нужными новыми уровнями.

Автоматическую конвертацию старых конфигов не делать: она перенесёт их исторические компромиссы и создаст трудно читаемый мусор. После того как новые способы запуска покроют нужные сценарии, старые классы и ветки удаляются отдельно.

> **Решение изменено 2026-08-19:** старые 41 уровня всё-таки конвертируются в новый формат отдельным контролируемым шагом. Перед конвертацией создаётся резервная копия исходных файлов. Это не постепенный runtime-адаптер, а одноразовая миграция данных, которую можно проверить и при необходимости повторить.

## Чек-лист реализации

Работа идёт небольшими шагами. После каждого пункта проект проверяется в Unity до перехода к следующему.

  - Откатить из него предзагрузку, применение стартовой машины, логику `Edit` и служебные флаги.
  - Откатить связанные временные изменения, которые были сделаны только для этой попытки (`PendingEditOrderModel`, применение его в `UniversalLevel`, временный UI `Edit`, кэш FindReferences и т.п.).
  - Отдельно не потерять изменения, не относящиеся к редактору.
  - Проверка: проект собирается и запускается в Unity; Debug Workshop продолжает открываться.

- [ ] **Создать новые классы и формат `LevelDef`.**
