# AI-детали для CarDesign

## Назначение папки

Рабочее пространство для создания автомобильных деталей версии 2 с помощью image-to-3D сервисов. Здесь хранятся исходные фотографии, подготовленные изображения для моделера, результаты разных сервисов и принятые игровые модели.

Работа отделена от разработки Unity-клиента. Цель этого направления — проверить и затем выстроить быстрый производственный pipeline целевого контента нового качества.

## Продуктовая цель

CarDesign остаётся казуальным конструктором. Игрок не моделирует инженерную конструкцию, но получает убедительный и узнаваемый результат.

Основной источник дизайна — реальные классические автомобильные детали известных моделей и эпох. Не нужно изменять удачную классическую форму только ради формальной уникальности. Важно сохранить узнаваемый язык автомобильного дизайна. Логотипы, маркировки производителя и случайный текст с исходных фотографий удаляются.

Первый тест должен ответить на вопрос:

> Можно ли достаточно быстро производить нужные CarDesign фары, решётки и бамперы с качеством, заметно превосходящим старые плоские детали?

## Начальный тест

Одни и те же три объекта прогнать через несколько сервисов:

1. Фара — глубина, линза, отражатели, диоды и разделение на материалы.
2. Решётка — тонкие повторяющиеся элементы и настоящие отверстия.
3. Бампер — длинные гладкие поверхности, симметрия и чистота topology.

Начальные сервисы:

- Tripo H3.1, включая multiview;
- Hyper3D Rodin;
- Meshy;
- один open-source вариант только после проверки коммерческих сервисов, если это даст полезное сравнение.

Не требуется выбрать один сервис для всех деталей. Допустим разный победитель для разных категорий.

## Задача нового чата

Для каждой детали пользователь передаёт несколько фотографий одной и той же детали и модификации автомобиля. Новый чат должен:

1. Проверить, что фотографии относятся к одной версии детали.
2. Выбрать главный ракурс и полезные дополнительные виды.
3. Отделить деталь от кузова и окружения.
4. Не делать буквальный рваный cutout по видимому краю фотографии.
5. Восстановить полный внешний контур детали.
6. Удалить логотипы, маркировки, номера и отражённый текст.
7. Упростить визуальный шум, вызванный бликами и отражениями.
8. Сохранить характерный реальный дизайн детали.
9. Достроить невидимый край и посадочную глубину как простую правдоподобную форму.
10. Подготовить согласованные изображения для image-to-3D сервиса.

Если исходных данных недостаточно, скрытая задняя часть не должна становиться сложной фантазийной конструкцией. Она нужна только для цельного объёма и может быть простой.

## Какие изображения готовить

### Master image

Главный нормализованный вид самостоятельного предмета:

- деталь целиком;
- чистый нейтральный фон;
- без кузова;
- без жёсткой падающей тени;
- без пересветов;
- сохранены реальные пропорции и внутренний рисунок;
- полный внешний контур;
- правдоподобная глубина.

Master image используется для обычного single-image generation и как основа остальных видов.

### Reference sheet

Лист из очищенных реальных фотографий:

- front;
- front 3/4;
- side;
- back, если доступен;
- отдельные крупные планы важных элементов.

Задача reference sheet — сохранить факты, а не создать красивую презентацию.

### Multiview sheet

Согласованные виды одного объекта:

- front обязателен;
- left/right при наличии информации;
- back только если он известен или нужен генератору;
- одинаковый масштаб;
- одинаковые пропорции;
- одинаковое количество внутренних элементов;
- нейтральный свет и фон.

Tripo API v3 поддерживает отдельный `multiview-to-model` endpoint минимум с двумя видами, один из которых front. Если Studio показывает только single-image режим, использовать Multiview/H Series, API или официальный ComfyUI workflow.

## Семантические части

Подготовленное изображение и полученная модель должны по возможности различать игровые роли:

### Фара

```text
Housing
Reflector
Lens
Bulb
LED
BodyColorPart — если элемент должен окрашиваться вместе с кузовом
```

### Решётка

```text
Frame
Chrome
BlackPlastic
Mesh
BodyColorPart
```

### Бампер

```text
MainBody
BodyColorPart
Chrome
BlackPlastic
Rubber
Light / Reflector — если встроены
```

Автоматическая segmentation считается заготовкой. Она должна проверяться вручную: визуальные части генератора могут не совпадать с нужными материалами игры.

## Что не поручать 3D-генератору

- `cutter` для отверстия в кузове — размечается вручную простой выпуклой геометрией;
- точный `LightAnchor` — добавляется в Unity;
- игровые pivot, scale и orientation;
- финальные `MaterialSlot`;
- проверку посадки на разных кузовах;
- окончательную мобильную оптимизацию.

## Критерии сравнения сервисов

Оценивать не preview на сайте, а экспортированный asset:

1. Соответствие реальной детали и её пропорциям.
2. Качество силуэта.
3. Настоящая геометрия против деталей, нарисованных в texture/normal map.
4. Глубина детали.
5. Симметрия там, где она должна быть.
6. Качество скрытой и задней стороны.
7. Разделение на семантические части.
8. Topology, тонкие треугольники, самопересечения и внутренний мусор.
9. UV и PBR maps.
10. Исходный и итоговый polygon count.
11. Время ручной очистки.
12. Количество неудачных генераций.
13. Стоимость одной принятой детали с учётом неудачных попыток.
14. Вид после назначения общих материалов CarDesign.
15. Вид на Android/iOS.

Предварительный критерий полезности: принятая деталь требует не более 30–60 минут ручной очистки. Порог можно изменить после первых тестов.

## Unity-ready результат

Принятая модель должна иметь:

- разумное количество полигонов для мобильной игры;
- удалённую невидимую и мусорную геометрию;
- понятные отдельные meshes или material slots;
- стабильный pivot;
- согласованную ориентацию;
- единицы масштаба, проверенные в Unity;
- отсутствие логотипов и случайного текста;
- сохранённые исходные PBR maps, даже если в игре будут назначены другие материалы.

После импорта в CarDesign добавляются:

- `MaterialSlot` для Housing, Chrome, Lens, Emissive и других ролей;
- `LightAnchor` для направления света;
- при необходимости Spot Light, emission и volumetric beam;
- вручную сделанный дочерний `cutter`;
- проверка через `BodyCutoutService`;
- иконка каталога после стабилизации материалов.

## Старые плоские детали

Старые фары с объёмом, запечённым в текстуру, не требуется массово переделывать. Они могут остаться базовым контентом или потенциальным LOD.

Новые ключевые детали версии 2 получают:

```text
реальную геометрию
→ раздельные материалы
→ отверстие в кузове
→ настоящую глубину
→ emission и свет
```

## Структура папки

```text
AI-детали/
├── README.md
├── PART_TEMPLATE.md
├── 01 References/
├── 02 Prepared Images/
├── 03 Generated Models/
└── 04 Accepted/
```

Внутри создавать подпапку по стабильному ID детали, например:

```text
headlight_porsche_911_classic/
```

Не смешивать фотографии разных модификаций в одной папке без явной пометки.
